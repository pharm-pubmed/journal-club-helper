# SPEC: Journal Club Helper — Critical Appraisal Chrome Extension for PubMed

Claude Code 引き継ぎ仕様書。v0.1（MVP）〜v1.0 の範囲を定義する。
UI・ストア文言はすべて英語。コード・コミット・ドキュメントも英語。この仕様書だけ日本語。

**戦略改訂: 2026-09-27。** 価格・人数・期間は検証用の仮説であり、実績や売上予測ではない。今回の改訂は事業方針のみで、有料機能・決済・計測を実装したことを意味しない。現状の実装と制約は `docs/HANDOVER.md` を参照。

## 0. 一言で

PubMed の抄録ページに張り付き、臨床家（レジデント・薬剤師・医学生）がジャーナルクラブや文献評価のためにやっている「批判的吟味」の型を、その場で埋められるようにする Chrome 拡張。
**要約はしない。吟味の型を提供する。** 要約ツールや汎用 AI も発表準備の代替手段になるため、実際の作業で比較する。

## 1. 背景と前提

- 初期顧客: まず紹介で接点を持てる、英語の論文を使う薬学レジデントまたは医学レジデントの小さな集団に絞る。国・職種を同時に広げず、最初に利用者 10 人を集められる領域を選ぶ
- 対象場面: 次の 30〜60 日にジャーナルクラブの発表予定があり、PubMed と PowerPoint / Word 等を行き来して準備している人。担当頻度・準備時間・自己負担できる金額は聞き取りで確認する。「全員が毎月使う」とは仮定しない
- 痛みの仮説: 論文から情報を拾うだけでなく、PICO・効果量・吟味の根拠を発表用の資料へ転記し直す手間がある
- 代替手段: 汎用 AI、既存の要約サービス、無料の計算機、手持ちの発表テンプレート。要約をしなくても準備時間の短縮という予算では競合する。「競合がない」は前提にしない
- 価値の仮説: **吟味した内容を、確認可能で編集しやすい発表資料に整える時間を減らす。** 抄録だけで吟味を完了できるとは訴求せず、全文で確認する項目を残す
- 位置づけは「教育・吟味の補助」。臨床判断の支援ではない。この線を UI 文言・ストア説明・免責で崩さない
- まず少人数でも採算と継続利用が成立するかを確かめる。12〜18 ヶ月での売却は事業成立の前提にしない（§10）

## 2. スコープ

### v0.1 MVP（無料機能のみ・サーバーなし）

1. PubMed 抄録ページで動く（`https://pubmed.ncbi.nlm.nih.gov/<PMID>/`）
2. 研究デザインの自動判定（Publication Type + 抄録キーワード、ルールベース）
3. PICO テンプレート（手入力。抄録からの候補ハイライトのみ）
4. 効果量の計算機（ARR / RRR / NNT / NNH、95%CI 付き）。抄録内の数値候補を検出して入力欄にプリフィル、確定はユーザー
5. デザイン別の妥当性チェックリスト（自作文言）
6. 1 枚サマリの書き出し（Markdown / クリップボード / プレーンテキスト）
7. 入力内容の PMID 単位ローカル保存

### v0.2 候補（需要確認後の有料ワークフロー）

8. 第一候補は編集可能な PPTX 書き出し。まず既存の Markdown 出力を使った見本で、転記・整形の手間が減るかを確認する。需要があった 1 種類のテンプレートだけを実装し、未実装機能を販売ページで提供済みとしない
9. AI 抽出（ユーザー自身の API キー持ち込み）は補助機能の候補。PICO・結果数値・限界・議論用の質問の候補を出す。AI の利用を有料価値の唯一の根拠にせず、API キーなしでも有料ワークフローが成立する設計にする
10. 課金は §4.8・§8 の検証に沿って小規模に導入する。年 $39 を最初の提示価格の仮説とし、先に決済システム一式を作り込まない

### v0.3 公開（既存の milestone 名）

11. 無料 MVP の Chrome Web Store 掲載、プライバシーポリシー、ランディングページ 1 枚。有料機能の完成を待たず公開・需要検証を進める

既存 issue との対応のため milestone 名は維持する。実行順は **v0.1 → 無料公開（既存 v0.3）→ 有料検証（既存 v0.2）**。実際のリリース番号は公開順に整理する。

### v1.0（有料利用の反応で決める）

- 発表テンプレートの追加・再利用など、既存顧客から繰り返し要望がある機能
- 小規模な教育プログラム向けの複数席契約（§4.8）。管理画面や共有サーバーは先に作らない
- Google Scholar / 主要ジャーナルサイト対応、クラウドでのチーム共有は初期の売上計画に含めない

### やらないこと（Non-goals）

- 論文の要約・平易化（既存ツールの領域）
- 全文 PDF の解析
- 臨床推奨・治療判断の出力
- 自前のユーザーアカウント、クラウド同期（初期段階では不要）。将来の決済サービス側の購入者情報・認証は別途開示する
- サーバーサイドの処理（AI もキー持ち込みで拡張から直接呼ぶ）

## 3. ユーザーフロー

1. PubMed 抄録ページを開く → ページ上部（Abstract 見出しの右）に小さな `Journal Club` ボタンが出る
2. クリック → Chrome Side Panel が開く（ページの DOM は改変しない。既存ツールの「消せないオーバーレイ」への不満を避ける）
3. パネル上部に自動判定: `Study design: RCT (parallel)` と判定根拠（Publication Type / キーワード）。手動で変更可
4. タブ構成: **PICO / Numbers / Validity / Export**
   - PICO: P・I・C・O の 4 欄。抄録内の候補語を薄くハイライト（クリックで欄に流し込む）
   - Numbers: 検出した数値候補をリスト表示（例: `12.3% vs 8.1%`, `HR 0.72 (95% CI 0.61–0.85)`, `45/300 vs 62/298`）。選ぶと計算機に入る。出力は ARR・RRR・NNT/NNH と 95%CI。CI が無限大をまたぐ場合は NNT→NNH の反転を明示
   - Validity: デザインに応じたチェックリスト（Yes / No / Unclear + メモ）
   - Export: 1 枚サマリのプレビュー → Copy Markdown / Copy plain text / Download .md
5. 入力は PMID 単位で `chrome.storage.local` に自動保存。同じ PMID を開けば復元
6. 有料候補（v0.2）: Export から発表用テンプレートへ書き出す。任意の AI 補助は `Auto-fill with AI` ボタンから利用し、初回のみ API キー設定を案内する。料金・提供範囲は §4.8 の検証後に確定する

## 4. 機能仕様

### 4.1 対象ページの検出

- URL パターン `pubmed.ncbi.nlm.nih.gov/\d+/` のみ。検索結果一覧では動かない
- PMID は URL から取得。ページ DOM の抄録テキスト、Publication Type、MeSH は DOM から読む。DOM 構造が変わった場合に備え、E-utilities `efetch`（`db=pubmed&id=<PMID>&retmode=xml`）へのフォールバックを用意する（API キー不要、3 req/s 以内、User-Agent にツール名とメール）

### 4.2 研究デザイン判定（ルールベース）

優先順位:

1. Publication Type: `Randomized Controlled Trial` → RCT / `Meta-Analysis` `Systematic Review` → SR-MA / `Observational Study` + キーワードで Cohort / Case-Control / Cross-Sectional / `Clinical Trial` のみ → Non-randomized trial
2. 抄録キーワード（`randomized`, `randomised`, `double-blind`, `prospective cohort`, `retrospective`, `case-control`, `cross-sectional`, `we searched`, `pooled`）でフォールバック
3. どれにも当たらない → `Unclear` として全チェックリストから選ばせる

判定ロジックは `src/lib/design-classifier.ts` に隔離し、ユニットテストを 20 件以上用意する。

### 4.3 数値検出と計算

- 検出パターン（正規表現、`src/lib/number-extractor.ts`）:
  - パーセント対比: `X% vs Y%`, `X% versus Y%`, `X% and Y%`（`vs` 前後が同一アウトカム文にある場合を優先）
  - 分数対比: `a/n1 vs b/n2`, `a of n1 ... b of n2`
  - 比: `RR|HR|OR (=|of)? \d+\.\d+ \(95% CI[,:]? \d+\.\d+[–-]\d+\.\d+\)`
- 計算（`src/lib/effect-measures.ts`）:
  - CER, EER → ARR = CER − EER, RRR = ARR / CER, NNT = ceil(1/ARR)
  - 分数入力時は Wald 法で ARR の 95%CI、NNT の CI は ARR の CI の逆数。ARR の CI が 0 をまたぐ場合は「NNT ∞ をまたぐ（NNT→NNH）」と表示
  - RR/HR/OR のみの場合: ユーザーに対照群イベント率（ACR）を入力させ、Cochrane Handbook 12.5.4 の方法で ARR/NNT を推定。OR からの換算は「イベント率が高いと過大評価」の注意を出す
- 出典表記: 計算式の横に `Cochrane Handbook §12.5` `CEBM Oxford` へのリンク（自分の言葉で説明し、引用はしない）
- 計算ロジックは全てユニットテスト対象。既知の教科書例（CER 0.26 / EER 0.16 → NNT 10 など）で検証

### 4.4 妥当性チェックリスト

- デザイン別: RCT / Cohort / Case-Control / Cross-Sectional / SR-MA / Diagnostic accuracy / Unclear（共通版）
- 各 6〜10 項目。項目文は **自作**する。CASP / JBI / CONSORT 等の既存チェックリストは文言を転載しない（CASP は非商用ライセンス）。概念（無作為化・割付隠蔽・盲検化・ITT・追跡率・交絡・選択バイアス・出版バイアス 等）は使ってよいが、質問文はゼロから書く
- 各項目: `Yes / No / Unclear` + 任意メモ。項目ごとに「なぜ重要か」の 1〜2 文ヘルプ（自作）
- 項目定義は `src/data/checklists/*.json` に置き、コード変更なしで文言を直せる

### 4.5 書き出し

- 1 枚サマリの構成（固定順）:
  1. Citation（著者・誌名・年・PMID・DOI）
  2. Clinical question (PICO)
  3. Study design（判定と根拠）
  4. Key results（絶対効果を必ず含む。相対効果しか無ければ「絶対効果は抄録に無し」と明記）
  5. Validity（チェックリストの Yes/No/Unclear 一覧と、No/Unclear の項目のメモ）
  6. Bottom line（ユーザー入力の 1〜2 文。空なら空欄のまま出す。生成しない）
  7. Discussion questions（v0.2 の AI 機能。無料版は空欄テンプレ）
- 形式: Markdown（見出し・表）、プレーンテキスト、`.md` ダウンロード
- 免責を末尾に固定で 1 行: `Generated with <name> for educational purposes. Verify against the full text.`

### 4.6 保存

- `chrome.storage.local` に `appraisal:<PMID>` キーで JSON 保存。上限を超えたら古い順に削除（最大 500 件）
- 設定は `settings` キー。API キーは `chrome.storage.local`（sync には絶対に入れない）
- エクスポート/インポート（JSON 一括）を設定画面に用意する

### 4.7 AI 抽出（v0.2 候補・課金範囲は検証後に確定）

- プロバイダ: Anthropic（`anthropic-dangerous-direct-browser-access: true` ヘッダで拡張から直接呼ぶ）、OpenAI。まず Anthropic のみ実装し、抽象化して後から追加可能に
- 送るのは抄録テキスト・タイトル・Publication Type のみ。ユーザーの入力メモは送らない
- 出力は JSON スキーマ固定（PICO 4 欄、数値候補の配列、限界候補の配列、議論質問の配列）。パース失敗時は再試行 1 回、それでも失敗なら「手動で入力」に戻す
- 生成結果は必ず「候補」として表示し、ユーザーが Accept しない限り欄に入らない
- レート・コストの表示: 1 回あたりの概算トークン数と料金の目安を設定画面に記載
- プロンプトは `src/prompts/*.md` に置き、コードから分離

### 4.8 マネタイズ戦略（検証後に課金を実装）

#### 誰の何に課金するか

初期は個人向けの小さな有料プランを検証する。購入理由の仮説は「発表のたびに資料を整える手間が減ること」。API キーの取得や API 利用料を追加負担に感じる人も想定し、BYOK（キー持ち込み）の AI 抽出だけを有料にする旧案は採用しない。

| 区分           | 提供範囲                                                                                                           | 位置づけ                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Free           | 現行の研究デザイン判定、PICO 手入力、数値計算、チェックリスト、Markdown / テキスト出力、ローカル保存・バックアップ | 吟味と 1 枚サマリを最後まで完成できる。既存の無料機能を後から狭めない。保存容量などの技術上限は維持              |
| Pro 候補       | 確認済みの入力を編集可能な PPTX に整形。まず 1 種類の発表テンプレート                                              | 年 $39 の仮説。AI キーなしでも使える価値を試す。自動で結論や臨床推奨は作らない                                   |
| 任意の AI 補助 | ユーザーのキーで抽出候補を作成し、確認後に採用                                                                     | 無料ベータで設定完了率と修正負担を確認してから提供範囲を決定。API 利用料は別途、運営による無制限 AI 提供はしない |

年額は月額が最適と判明した結果ではなく、低単価での請求・運用を簡単にするための出発点。最初は年 $39 の一案を提示し、少人数を複数の価格群に分けない。年 $29〜49 を見直し範囲の目安とするが、未購入の理由が利用頻度や価値不足なら値下げだけで対処しない。単発の発表にしか使われない場合は、自動更新の年額販売を拡大せず、期間限定の買い切りを別に検証する。無期限サポート付きの lifetime プランは設けない。

#### 販売までの順序

1. 無料版を使って発表準備を観察し、資料整形が実際の負担かを確認する。見本は見本と明示し、まだ決済は受けない
2. §8 の利用ゲートを通ったら、PPTX テンプレート 1 種類の最小版を作る。発表予定に合わせて 14〜30 日間試せるようにし、カード登録や自動課金を試用条件にしない
3. 実際に使える有料機能を試した人に、同じ年 $39 の条件で購入を案内する。更新・解約・返金条件、API 料金が別であることを購入前に示す。アンケートの「払いたい」と、返金を除いた実購入を区別する
4. 最初の 5 人の購入と次回利用を確認してから機能追加に進む。年額購入だけで翌年更新を見込まず、更新率は実際の更新時期まで未測定とする

#### 決済と運用

- ExtensionPay を第一候補とするが未採用。公式には月額固定費なし・取引ごと 5% とされ、Stripe 側の決済等の費用も別に見積もる。実装直前に料金・対応国・契約条件を再確認する（§14）
- 無料公開や購入意向の検証を、決済アカウントの移管確認で止めない。課金導入前に移管・データ出力・返金・購入復元の手順を調べて記録する。移管できないという理由だけで自前の課金基盤を作らず、売上見込みと開発・保守負担を比較する
- 課金導入時に `src/lib/license.ts` へ判定を分離し、オフラインでの期限付きキャッシュと購入復元を設計する。期限切れでも保存データの閲覧と既存の無料出力を妨げない
- 決済・ライセンス照会は外部通信となる。「外部通信なし」「アカウント不要」等の文言、プライバシーポリシー、権限を実装に合わせて更新してから公開する。現在の無料版の説明を先に有料版の説明へ置き換えない

#### プログラム向け販売は第二段階

個人の有料利用が続き、少なくとも 2 人の教育担当者から予算・購入時期・対象人数を確認できた場合のみ、10 席・年 $199〜299 程度の小規模パイロットを検討する。この金額も仮説。利用者と予算決裁者を区別し、請求書で購入できるか、Chrome 拡張を導入できるかを確認する。席の付与・入替・失効と購入復元が実際に運用できることを販売条件とする。共有機能・管理画面・SSO を先に開発せず、法人契約の売上は基本ケースに含めない。

## 5. 技術スタック

- Manifest V3、TypeScript、WXT（または Vite + CRXJS。WXT 推奨: MV3 の定型を減らせる）
- UI: Preact + 最小の CSS（Tailwind は使わない。パネルは軽く、外部フォント不要）
- Side Panel API（Chrome 114+）。Edge / Brave でも動くことを確認
- テスト: Vitest（lib 層）、Playwright（PubMed 実ページでのスモーク 3 本）
- CI: GitHub Actions で lint / typecheck / test / zip ビルド。Web Store へのアップロードは手動（v0.3 以降で自動化検討）
- 依存は最小。数式・正規表現・保存はすべて自前

### 権限（最小）

```
"permissions": ["storage", "sidePanel", "activeTab"],
"host_permissions": ["https://pubmed.ncbi.nlm.nih.gov/*"],
"optional_host_permissions": ["https://eutils.ncbi.nlm.nih.gov/*", "https://api.anthropic.com/*", "https://api.openai.com/*"]
```

- E-utilities と AI プロバイダはユーザーが機能を有効化したときに `permissions.request` で取得
- `tabs`、`<all_urls>`、`scripting` は使わない（ストア審査と売却時の評価の両方に効く）

## 7. 検証方法（プライバシー優先）

- 外部アナリティクス・テレメトリは導入しない。ローカルの起動・書き出し・AI 実行回数はユーザー向け表示であり、運営側が閲覧できる全体指標ではない
- 同意を得た少人数の協力者について、開始日、発表予定、初回サマリ完成、次の発表での再利用、準備時間、資料修正時間、価格提示、購入・返金、問い合わせ対応時間を手動で記録する。連絡先と検証記録は分離し、不要になった連絡先は削除する
- 完成は「自分の発表用サマリを書き出せた」、再利用は「別の発表・論文でも使った」と定義する。待機リスト登録・インストール数だけでは価値を証明しない
- 時短は本人の通常の準備と比較し、AI の訂正や全文確認、出力後の整形も含める。少人数の自己申告値であることを明記し、一般利用者全体への効果を断定しない
- Web Store の指標は流入の参考。面談・利用観察・決済記録と混ぜて転換率を計算しない。決済後の購入者情報の扱いは課金導入時に開示する

## 8. 成功指標・採算・判断ゲート

### 8.1 最初の 90 日で何を確かめるか

以下は小規模事業の投資判断用の目安で、市場平均や統計的な有意差ではない。起点は無料版を協力者に渡せる日。聞き取り・試作・初期導入に使える時間の仮置きは週 4 時間、最初の 90 日で最大 50 時間。時間を確保できなければ締切を延ばし、期限のために機能を増やさない。

| 時点          | 確認すること                                                                                                                                        | 次に進む条件・届かない場合                                                                                                          |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 0〜30 日      | 対象者 10 人の実際の準備を確認。うち 6 人以上が自分の論文でサマリを完成                                                                             | 未達なら導入・初回体験か顧客の選び方を修正。有料機能の本実装は待つ                                                                  |
| 31〜60 日     | 初回完成者のうち、次の発表機会が来た人数を分母に再利用を記録。4 人以上の再利用と、3 人以上から資料整形への具体的な困り事・年 $39 での試用希望を確認 | 達成したら PPTX 1 種類の試作へ。次の機会がなければ未判定とし、月額継続率に置き換えない。人数・分母を併記                            |
| 61〜90 日以降 | 動く有料候補を試用した適格者 10 人へ同じ価格を提示し、返金確認期間後に 3 人以上が実購入                                                             | 3 人は追加検証の根拠であり黒字化の証拠ではない。最初の 5 人の購入・次回利用まで少人数で継続。試作品の準備が遅れたら検証期間を延ばす |
| 拡大前        | 最初の有料 5 人中、次の発表機会が来た 3 人以上が再利用。対応時間・返金理由・実際の手取りを記録                                                      | 対応コストに見合い、同じ獲得経路で次の顧客に届く場合に限って拡大                                                                    |

ここで適格者とは、自分の発表用に試用を完了した対象顧客を指す。初回の 10 人から足りなければ同じ条件で追加募集し、募集人数・試用脱落者数も残す。友人からの応援購入は別に集計する。

対象者 10 人に使える有料版を提示して購入が 0〜1 人なら、有料機能の追加を止め、未購入理由を聞く。2 人なら追加の小規模検証にとどめる。対象顧客または提供価値を一度見直しても改善しなければ、無料の小規模ツールとして維持するか開発停止を判断する。無料機能の制限強化を既定の対策にしない。

### 8.2 売上の規模感

年 $39 を全員が契約した場合の**手数料・返金・税・経費控除前**の計算。顧客数はシナリオであり獲得予測ではない。

| 有料契約数 | 年換算売上 | 月換算売上 |
| ---------- | ---------- | ---------- |
| 5          | $195       | $16.25     |
| 50         | $1,950     | $162.50    |
| 150        | $5,850     | $487.50    |
| 308        | $12,012    | $1,001.00  |

月換算売上は毎月の入金ではない。自動更新の契約なら MRR の参考になるが、年額の更新実績・解約予定は別に管理する。単発ライセンスや手作業の資料作成サービスを試す場合、その売上は MRR に含めない。

旧案の年 $29・利用者 500 人・有料転換 2% なら 10 契約、年 $290、月換算約 $24。年 $39 でも月換算 $1,000 には 308 契約が必要で、仮に転換 2% なら同じ観測期間・定義の対象者が 15,400 人必要になる。週間アクティブ人数と価格提示を受けた人数を混同しない。このため「12 ヶ月で MRR $1,000」は確約する目標から外す。

### 8.3 コストを含めた継続判断

- 現金収支: 売上 − 返金 − 決済・為替等の費用 − ドメイン等の固定費 − 外注費。AI は BYOK の間はユーザーが直接負担するが、設定支援の時間は運営コストに入れる
- 工数込みの採算: 現金収支 −（集客・開発・保守・問い合わせの時間 × 自分で定める時間単価）。既存の開発時間は埋没費用として分け、追加投資を回収できるかを見る
- 例として、手数料等を売上の 10%、固定費を年 $120、運営を月 4 時間 × $25 と仮置きすると、必要契約数は `ceil((120 + 4 × 12 × 25) / (39 × 0.9)) = 38`。これは継続運営だけの試算で、返金・税・初期開発費は含まない。最初の 50 時間も $25/時で初年度に回収するなら 74 契約が必要。10% は決済会社の公定料率ではなく感度分析用の仮定
- 50 契約でも上の仮定では年 $1,635 が固定費控除後・工数控除前、工数控除後は年 $435 にとどまる。初年度開発費を含めれば赤字。対応時間が増えれば必要人数も増えるため、売上だけで成功と判断しない
- 有料広告は初期には使わない。紹介経由でも獲得に使った時間を記録し、実際の継続と年間の手取りが分かるまで広告費の上限を正当化しない

## 9. リスクと対策

- 汎用 AI や要約ツールで十分と言われる → 実際の発表準備で比較し、訂正・転記を含む時短が出ないなら有料開発を止める
- 担当頻度が低い / API キー設定で離脱する → 次の発表機会での再利用を測り、AI なしの価値を優先する。継続需要がなければ年額課金を拡大しない
- 少額売上に対して問い合わせが多い → 顧客ごとの対応時間を記録し、提供範囲・価格・継続可否を見直す
- PubMed の DOM 変更 → E-utilities フォールバック、Playwright スモークを週次で CI 実行
- 数値抽出の誤り → 自動確定しない。必ずユーザーが選択・確認する UI
- 臨床判断ツールと見なされる → 文言は education / appraisal に統一、免責固定、推奨は出さない
- チェックリストの著作権 → 文言自作。既存チェックリスト名を出す場合は「〜と同様の概念」までにとどめる
- MV3 の Service Worker が落ちる → 状態はすべて storage に置き、background は極小に

## 10. 継続運営と将来の移管

- 売却は選択肢として残すが、時期・買い手・評価額を事業計画の前提にしない。まず 6〜12 ヶ月の利用、売上、費用、対応時間を記録する
- プロジェクト専用の Google / GitHub / 決済アカウント（独自ドメインを取る場合はそれも）を使い、個人の資産・認証情報と分ける。移管可能性は各サービスの現行手順を調べて記録し、可能と推測しない
- `docs/HANDOVER.md` にアカウント一覧、ビルド・公開手順、既知の問題、外部依存を残す
- 収益・費用を分離して記録する。年額の入金をその月の利益として使い切らず、残存契約期間の運営・返金に備える
- 自前の決済基盤や売却準備に時間を使うのは、実際の収益と移管要件で必要性が説明できる段階からにする

## 11. 次の実行順と集客

1. 現行 MVP の無料公開準備を終える。LP では「PubMed で吟味し、1 枚のサマリへ書き出す」という現行機能を、実際の出力例と短い操作動画で示す。有料機能を先に約束しない
2. 最初の 2 週間で、既知の同僚・教育担当者を通じた紹介先 5〜10 人を探す。目標はインストール総数ではなく、次の発表で使ってくれる 10 人。接点がない場合は公開の募集先を 1 つずつ試し、対象者に届かなければ顧客層を見直す
3. 1 人 20〜30 分の利用観察と、次の発表後の短い聞き取りを行う。協力者への謝礼がある場合は購入額と分け、補助された購入を通常の需要として数えない
4. 紹介以外の経路として、教育担当者向けの実演や 1 論文の使用例を試す。Reddit 等は各コミュニティのルールと必要な管理者許可を確認してから、役立つ実例とともに募集する。一斉投稿や有料広告を前提にしない
5. §8 の利用ゲートを満たしてから有料候補を試作し、試用 → 同一価格の提示 → 購入・再利用の確認へ進む。AI UI や課金の既存 issue はこの順序に合わせて見直す。AI 抽出コアが実装済みでも、AI 課金の需要が確認済みとはみなさない

この仕様書の改訂だけで外部への連絡・投稿・請求は行わない。GitHub の既存 issue / milestone は未更新で、着手時にこの方針との相違を整理する。
